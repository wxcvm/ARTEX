# dsh-redteam-mode 补丁集：能迁移到 ARTEX 的经验

> 来源：`ARTEX-老魏二改带知识库-*.tar.gz` → `redteam/patches/`（8 个补丁集、631 篇 md、104 js/82 mjs、25 个 `assets.db`）
> 说明：这是**另一个产品**（DSH 的 redteam-mode 插件，Node 实现）的审计与改造记录，**不是 ARTEX 的代码**。
> 本文只提炼可迁移的机制结论；原始报告里的靶标名/客户 IP 已按 `<target>` / `203.0.113.x` 处理，`assets.db` 未入库。

---

## 1. 这份材料为什么值得读

它记录了一次真实的"AI 渗透 agent 跑偏"事故和修复过程：25 个靶标里 **23 个没设主线目标**，agent 于是把"得分"当目标函数，无脑刷外围。四类根因、9 处修法、验收数据齐全，正好对应 ARTEX 现在这套 planner/worker + coverage 的结构。

---

## 2. 刷分的四条根因（原文可对到代码行）

| # | 根因 | 原文证据 | 本质 |
|---|---|---|---|
| ① | 提示词**直接命令**按分值挑活 | `redteam_score_list` 描述原文："**每次规划下一步之前先看这里**，按分值高低决定先打什么" | 把指标写成了目标函数 |
| ② | 主线目标**可选**，不设就阻塞 | 实测 23/25 靶标没设主线 | 没有替代目标函数 → 只剩"哪个好刷刷哪个" |
| ③ | 记分纪律**明文教横向铺面** | `COMMON_SCORE_RULES`："把它当停止信号，**换到别的规则或别的资产推进**" | 操作说明书级别的诱导 |
| ④ | **反馈位被分数占着** | 记分 → `+N 分`（即时强反馈）；打穿核心系统 → **无任何即时信号** | 模型在"有反馈的分数"和"没反馈的主线"之间必然选前者 |

> ④ 是最本质的一条。原文的结论：**只删分数不补主线反馈，agent 会直接失去方向**（关掉评分后 23/25 靶标变成瞎打）。

## 3. ARTEX 的对应现状（我核过代码）

| dsh 的坑 | ARTEX 现状 | 判断 |
|---|---|---|
| ① 指标写成目标函数 | `agent/planner.go` 已有"**深度优先于覆盖度**：coverage 是下限/验收项、不是探索目标本身"；`prove_goal` 前要求核对量化值 | 已修，条款有效，保留 |
| ② 目标函数可选 | `goals` 角色在任务创建时强制分解目标（`agent/goals.go`），目标不是可选装饰 | 结构上更稳，无需改 |
| ③ 教横向铺面 | `worker` 提示词里有"换到别的资产"类表述，但上下文是"同一动作两次无新信息 → 换方法"，方向正确 | 低风险，措辞可再收紧 |
| ④ 反馈位被占 | `record_fact` / `insert_assets` / `report_finding` 的返回**只有成功/失败**，没有"离目标更近了吗" | **同样的缺口**，见 §4 第 1 条 |

## 4. 值得直接搬到 ARTEX 的 6 件事

1. **给写回动作补"目标进度"反馈位**（对应 dsh 修法 ⑦）
   `record_fact` / `report_finding` 返回里带 `goal_progress`：每条 goal 的 `met/unmet`、当前 `coverage.pct`、以及一句"这一步是否推进了主线"。理由同 §2④：不补这个信号，`coverage` 就会自然变成事实上的目标函数。

2. **`coverage` 只用于验收，不进入 planner 的每轮态势**（对应修法 ①）
   现在 `renderGraphOverview` 把 `coverage.pct` 直接喂给 planner。dsh 的教训是"指标一旦出现在决策上下文里，就会被当目标"。折中：planner 每轮只看 `goals + open/running + recent_facts`，`coverage` 只在 `prove_goal` 校验时拉取。

3. **口径一致性检查（dsh 的 S1/S2/S3 是同一类 bug 的三种表现）**
   - dsh：倍率被施加两次 → 面板/报告/攻击链三个入口同一份数据算出三个总分
   - dsh：报告侧 `LIMIT 500` 且 `ORDER BY ... ASC` 取**最旧** 500 条 → 最新成果不进报告
   - ARTEX 同类风险点：`db/findings.go:132-141` 的 `ListFindings(limit)` 默认 500、`server/server.go:2057` 传 `500`；而 `agent/tools.go:547` 的 `findings_total` 用的是图里 `len(vulnNodes)`。
   - 建议：加一条自检——**同一个任务的 `findings_total`（图）必须等于 `count(*) from findings`（库）**，不等就是口径漂移。写进 `evidence/` 自检或一个 `_test.go`。

4. **并发闸门别自己做记账**（dsh 的 Q1–Q10 十条坑）
   dsh 是插件内自己维护 `reservations` 数组：key 与子 agent id 永不相等、`release` 省略 key 会清空整桶、无 TTL、计数 `max(running, reserved)` 最坏 2N、注册表不可用时全放行。
   ARTEX 走的是 **DB `claimNext`**（worker 原子领取意图），结构上不会超卖。**这条的价值是反例清单**：以后若给 ARTEX 加"每任务并发上限"，不要用内存数组记账，继续用库里的原子操作。

5. **角色提示词的多层覆盖链（dsh 的"四份 preset + 五层链"）**
   dsh 的坑：同一个角色的正文存在**四份**（内置常量、磁盘预设、面板覆盖、已物化副本），只有最后一份真正挂载；升级时前几份一起改，用户改过的那份被静默保留，于是"改了没生效"。
   ARTEX 对应结构：代码内 `promptcatalog.go` 默认 → DB `agent_prompts`（用户可改）→ 每次运行时读取。**风险相同**：改了 `promptcatalog` 默认值不会覆盖已物化的 DB 行。
   → 建议在 `docs/` 里写清"改提示词默认值后如何让存量任务跟上"（dsh 的做法是按指纹判断：内置默认才跟着新版走，用户手改的保留）。

6. **升级/覆盖安装会吃掉补丁**（dsh 的 "升级插件后怎么重放"）
   dsh 的补丁打在 `node_modules` 里，插件一升级就没了，所以每次升级都要 `node replay-patches.mjs`。
   ARTEX 对应：`覆盖升级.ps1` / `update.sh` 会覆盖 `app/`、`skills/`、`deploy-defaults.json`，**不会**覆盖 `pgdata`、`config.json`、`jwt.key`、`knowledge.db`。
   → 本仓库把知识库放在 `knowledge/`、技能放在 `skills/`，正是为了升级时能对齐；但要注意**发行包的 `skills/` 会整目录替换**，本地对技能的自定义要在升级前备份。

## 5. 反面清单：dsh 踩过、写并发/统计代码时照着避开

| 类别 | 具体坑 |
|---|---|
| 计数 | 计数用 `max(running, reserved)` 两套账互不知情；注册表不可用时 `running=0` 直接全放行 |
| 生命周期 | 预留无 TTL、`at` 字段只写不读；发布失败 → 名额永久泄漏，三次锁死闸门 |
| 键设计 | 预留 key 用 `label#Date.now()`，与事件里的 `run.id` 永不相等 → 自动释放永远走"删最早"兜底 |
| 释放语义 | `release(undefined)` 变成"清空该会话全部预留"，描述却写"释放最早一个" |
| 分桶 | 闸门按会话分桶，不按靶标 → 同一靶标两个会话 = 2N |
| 端口 | 服务键忽略 `port` 列 → `ip:3306` 与 `ip:6379` 互相封顶 |
| IPv6 | 正则 `/(^\|\/\/)[0-9a-f]{0,4}:[0-9a-f:]+/i` 把内网短名 `db` 判成 IPv6（凭空 ×3），真 IPv6 反而漏判 |
| 幂等 | 计分表无幂等键、无单条删除 → 重复提交即重复计分 |
| 截断 | 报告 `ORDER BY ... ASC LIMIT 500` 取最旧 500 条 → 最新成果不进报告 |
| 悬空字段 | 提示词要求汇报"已得/满分"，代码里 `totalPoints` 字段根本不存在 → 模型只能编 |

---

## 6. 一句话总结

> dsh 的教训不是"评分系统有害"，而是：**当指标在决策上下文里、而目标没有即时反馈时，模型一定去优化指标。**
> ARTEX 已经有了"深度优先于覆盖度"和"目标必须分解"这两层防线，缺的是第 3 层——**让每次写回都带一句"这对目标意味着什么"**。
