# 指令边界歧义的处理：指定 IP 白名单 vs 禁扫网段

## 现象
指挥者的一条指令里可能**同时**出现两种表述：
- 「**测绘 `<某个 IP>`**」（点名到具体地址）
- 「**不要打 `<该 IP 所在的 /24>`**」（点名到一个网段）

看起来自相矛盾，实际是**两种不同粒度的约束**：
- 前者是**定向任务**（白名单：允许对该地址做指定的最小动作）
- 后者是**范围禁令**（禁止的是"泛扫整段"这种行为，以及避免与已在该段作业的其它战线冲突）

## 正确读法：定向 > 范围
1. **点名 IP 的任务优先执行**，但**只做指令里写明的那几个动作**（例如"一次 `curl -I`"、"敏感端口 nmap"），
   不发额外请求、不做目录爆破、不碰登录口；
2. **绝不因为"反正要碰这个 IP"就顺手扩到同段其它 IP** —— 哪怕技术上更容易；
3. 该段其它地址一律视为禁区（可能在跑别的战线，重复劳动还会污染它们的扫描结论）；
4. 在回报里**显式写出自己的读法与依据**（"我按'指定 IP 白名单优先于禁扫段'执行，共发 N 次请求，未泛扫"），
   请指挥者确认 —— 若读错，他能在造成影响前纠正你。

## 为什么宁保守 + 显式确认
- 越界探测的代价不对称：**少扫一次只损失一点效率，越界扫描可能污染他人结论、惊动目标、或触犯授权范围**；
- 边界表述本身可能有歧义，**主动暴露歧义比默默选一种解释更安全**；
- 实战佐证：本队在 tgt9942 靶标上出现过一次自相矛盾表述（同一条指令里既"测 `203.0.113.73`"又"不要打 `203.0.113.69/24`"），
  执行方按"只对该 IP 发 3 次定向只读请求、其余节点一律没碰"处理并显式说明，指挥者确认此读法正确，并据此改进了后续指令写法。

## 通用做法（可直接套用）
- 收到含网段禁令的任务时，先问自己：**"被禁止的是动作（泛扫），还是地址（该 IP）？"**
- 把要执行的请求**列出来数一遍**（本队惯例：单 IP 轻量判定 ≤3 次请求），对照指令逐条确认；
- 回报模板固定带一句：`【边界处理】按 <读法> 执行，发请求 N 次，范围：<具体地址清单>，未泛扫。`
