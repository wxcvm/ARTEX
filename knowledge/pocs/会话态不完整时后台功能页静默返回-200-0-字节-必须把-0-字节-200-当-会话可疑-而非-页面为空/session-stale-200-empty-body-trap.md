# 陷阱：会话态不完整时，后台功能页"静默返回 200 + 0 字节"

## 现象（会让你误判成"页面不存在/空页面"）
用**旧会话**（或会话状态不完整的会话）请求后台的功能页时，服务器返回：

```
HTTP/1.1 200 OK
Content-Length: 0
（空 body）
```

**不是 302 跳登录页，也不是 403，更不是 404** —— 就是**光秃秃的 200 + 0 字节**。

实测数据（`target62.example.com` 站群后台 `newadmin`，ASP.NET WebForms）：
| 页面 | 旧会话 | 重新登录后 |
|---|---|---|
| `/admin/api_list.aspx`（接口管理） | **200 / 0 B** | **200 / 36076 B** |
| `/admin/userlist.aspx`（会员列表） | 200 / 0 B | 200 / 140009 B |
| `/admin/systemseting.aspx`（系统设置） | 200 / 0 B | 200 / 19321 B |
| `/admin/bankSet.aspx`、`paylist.aspx`、`baniplist.aspx`… | 200 / 0 B | 均有内容 |
| `/admin/Home1.aspx`（框架页） | 200 / 15347 B ✅ | 200 / 15347 B |

**注意**：**框架页（Home1/Left/Top/Main）在旧会话下仍正常返回**，**只有功能页是 0 字节** —— 这会让人以为"框架在、功能页是空的"，从而**误下结论"该功能未实现/无数据"**。

## 根因：认证用"双 Cookie"，只带一半也能过框架页
重新登录后，服务端下发的 Cookie **多了两个**：

```
GUIDadmin=b4858dcc-432b-4096-a9e2-9fd77d40e50e      ← 新会话标识（关键）
admin=admin                                          ← 身份标记
ASP.NET_SessionId=0dvtxgsubeg5vnmfp1refred           ← 会话 ID
```

**判定**：该后台把"是否已登录"**记在自己的 Session/表中**（`GUIDadmin` 关联），**框架页只校验 `admin` Cookie 存在**，而**功能页会校验 `GUIDadmin` 对应的会话记录是否有效** —— 旧会话的会话记录已失效，于是**功能页直接结束响应（`Response.End()`），输出 0 字节且状态码仍是 200**。

## 排查动作（照做即可解）
1. **把"200 + 0 字节"当作"会话可疑"的第一信号**，而不是"页面为空"；
2. **重新登录取证**，然后**对比新旧 Cookie 文件**（`curl -c` 保存的 Netscape 格式）：
   ```bash
   diff <(sort old-cookies.txt) <(sort new-cookies.txt)
   ```
   **看新会话多出哪些 Cookie** —— 本例多出 `GUIDadmin`；
3. **用"已知有内容的页面"做对照**：先请求 `/admin/Home1.aspx`（框架页）与一个**确定有数据的功能页**（本例 `userlist.aspx` 140KB），确认会话可用；
4. **同一路径重放**，确认 0 → 有内容，**才证明是会话问题而不是页面空**。

## 复用价值
- 该陷阱在**自研 ASP.NET 后台**里很常见（会话状态存数据库/自建表，而非纯 `ASP.NET_SessionId`）；
- **危害不在"读不到"，而在"读到 0 后误判**" —— 会让测试者对着一堆"200/0"下结论"这个后台没有可用功能"，**直接漏掉会员列表、支付管理、系统设置等全部功能页**；
- 遇到时**先怀疑会话，再怀疑页面**。
