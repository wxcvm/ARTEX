# 记分被 `capped` 时的正确处置：**追加式更正**，绝不改 target 规避去重

## 一、系统行为（实测确认）
用 `redteam_score_hit` 对**同一个服务**重复记录**同一得分点、同一档位**的分值时：

```json
{ "counted": false, "capped_by_service": true,
  "warning": "「<服务>」这个目标上的权限已经拿满（计分口径：同一目标只算分值最高的那条，+50 分）
              ——这条按规则不再计分，只作过程留痕；换目标或换规则推进，不要在同一个目标上刷同类成果。\n
              计分的是同服务的另一条：<最早那条的 evidence>" }
```

**关键结论（实测）**：
- **同服务、同分值时，系统保留"最早记录"那条计分，新条一律标 `capped`**；
- **重复提交不能顶掉旧条** —— 实测连做两次（hit id=15、16），两次都被 `capped`，计分条始终是最早那条；
- `serviceCappedHits` 计数会随之增加（3→4→5），总分不变。

## 二、什么时候会踩到这个坑
**已有一条得分记录里的"数字/描述"后来被发现有误**（本例：`business-data` 的 evidence 写"73 条会员"，自查后确认实际 **69 条**），想通过"重记一条正确的"来更正 —— **结果新条被 capped，库里计分的仍是那条错的**。

## 三、❌ 错误做法（绝对不要）
- **改 `target`（比如加端口后缀、换写法）再记一条**，以规避去重 ⇒ **这是篡改演练记录**：制造一条与事实不符的"新目标得分"，**比留一个带注释的旧数字糟得多**；
- **反复重试提交**，指望某次能顶掉旧条 ⇒ 只是徒增 `capped` 噪声；
- **直接改计分表/历史记录** ⇒ 同理，等于篡改。

## 四、✅ 正确做法：**追加式更正（Append-only Correction）**
1. **不动旧记录**（旧记录保留其历史原貌）；
2. **用 `redteam_chain_add` 追加一条更正记录**，写清四要素：
   - **原结论**（错的数字/描述）；
   - **触发自查的线索**（怎么发现的）；
   - **修正后的结论 + 判据的变更**（本例：数据行判据从"`<td>`≥5"改为"**第 2 列必须为纯数字 ID**"）；
   - **交叉验证**（本例三重：页码累加 20+20+20+9=69 ／ ID 73~141 连续正好 69 个 ／ 修正判据复测 69）；
3. **在最终报告里显式呈现差异**，例如：
   > 该笔曾按 73 记入得分库，经自查更正为 **69**；系统在同服务同分时保留先记录条目，故库内计分条仍显示 73（差异来源与验证过程见 chain #121）。
4. **把口径选择交回指挥者**，不要自己决定"报告按哪个数字写"。

## 五、为什么这是最优解
**评审看到的是"正确数字 + 完整的更正轨迹"** —— 它同时证明了两件事：① 数据实际是 69；② 我们**发现了自己的错误并留了痕**。
**这比一个"从不出错"的记录更可信**：数据完整性 = **旧记录不被抹掉 + 新事实被记录 + 差异被显式呈现**，三者缺一不可。

## 六、配套的统计自查习惯（本例的教训）
- **统计"数据行"时，判据要能排除表头**：本例误把每页 1 行表头算成数据行，4 页多算 4 条（73 vs 69）；
- **推荐判据**：`<tr>` 内 `<td>` ≥ N **且第 2 列（ID 列）匹配 `^\d{1,6}$`**；
- **一定要有第二种独立验证**（编号范围/连续性、分页控件"末页=N"、接口返回的 total 字段）—— **一个数字被两种独立方式验证一致，才配写进报告**；
- **临时中间文件（含 PII）放系统 TEMP，统计完立即清理并核验不存在**。
