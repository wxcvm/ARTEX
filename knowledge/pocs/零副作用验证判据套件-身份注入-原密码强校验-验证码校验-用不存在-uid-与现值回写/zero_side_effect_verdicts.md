   (A) $request->userId 能否被客户端覆盖（身份注入原语是否存在）
   (B) 改密/换绑类接口是否真的强校验原密码/验证码
   (C) 验证码绑定类接口是否校验验证码

设计原则：只用「不存在的目标标识」和「与现值相同的写入值」，把最坏情况的副作用压成 0。

================= (A) 身份注入判定：只读 oracle + 不存在的 uid =================
变体（全部只读、全部带自己的合法 token）：
  V0 基线            GET  /…/info
  V1 ?userId=1       GET  /…/info?userId=1            # 1 = 真实他人
  V2 ?uid=1          GET  /…/info?uid=1
  V3 ?userId=1&uid=1&id=1
  V4 头 userId/X-User-Id/uid
  V5 body {userId,uid}（POST 到同一个只读方法）
  V6 ?userId=999999  GET  /…/info?userId=999999      # 关键：不存在的 uid
判据：
  * V1~V5 与 V0 响应逐字节一致  ⇒ 参数被忽略
  * V6 返回「自己的」数据（响应里带自己的账号名）⇒ 参数被忽略（而不是报“用户不存在”）
  * V6 报「用户不存在/500/空」而 V0 正常 ⇒ **注入可能成立**，此时换写接口用不存在的 uid 复核
写接口复核（**必须用不存在的 uid**，天然无法写到任何人）：
  POST /…/set-password     {"userId":999999,"oldPassword":"000000","newPassword":"000000","confirmPassword":"000000"}
   · 回 1005/“用户不存在” ⇒ 注入成立（危险，立刻停止，报告）
   · 回 1001/“原密码错误”（落回自己账号）⇒ 注入不成立

================= (B) 强校验判定：new == old =================
判据设计：把 newPassword 与 oldPassword 设成**同一个值**。
  * 若校验存在   → 回「原密码错误」，无任何改动
  * 若校验被绕过 → 写入的值与… 不对，仍会写。所以再退一步：old=new=「一个当前一定不成立的值」。
    实测做法：oldPassword=newPassword=confirmPassword="000000"：
      · 校验存在 → 1001 原密码错误（零改动）
      · 校验缺失 → 密码被设成 "000000"（自己的账号，可自恢复，属可接受副作用）
  ★ 若连这一步都不愿承担：改为对「不存在的 uid」发同样的请求（见 A 的写接口复核），
    既能判定注入又能判定校验顺序，副作用严格为零。

================= (C) 验证码校验判定：用现值回写 =================
思路：把「当前库里已经存在的值」再绑一次，附一个**从未下发过的假验证码**。
  POST /…/phone/bind {"phone":"<该账号当前绑定的手机号>","code":"000000"}
  * 回「验证码错误/已过期」 ⇒ 校验生效
  * 回「保存成功」        ⇒ **校验被跳过**（而此时写入值 == 现值，净变化严格为 0）
同理 email。
取「当前绑定值」：很多系统会同时返回脱敏值与明文（如 phone / phoneRaw），
若只有脱敏值，就先用自己注册时的号码记录一份。

  * 不要为了确认验证码缺陷而改绑到全新号码（会占用他人号码 / 改动真实账号状态）；
    如需百分之百确认，请在有可控号码的前提下再补一发，并事先取得授权。
