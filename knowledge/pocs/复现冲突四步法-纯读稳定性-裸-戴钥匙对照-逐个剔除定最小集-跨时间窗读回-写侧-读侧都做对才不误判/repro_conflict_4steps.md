## 适用场景
两个测试者对同一"未认证写"得出**相反结论**（一个说真写、一个是假阳性/假阴性）。本战役真实发生过：`/Tk_Kj/zan2` 我判定"未认证写成立"，另一路判定"复现不出来"，最后查明**两边都没说谎**，是两侧判据各缺一半。

## 四步法（写侧两步 + 读侧两步，缺一步就会误判）

### 第 1 步 · 纯读稳定性检验（读侧）
**不发任何写请求**，对读回接口连读 5 次：
```
.58 连读 5 次 → zanshu = [7,7,7,7,7]   ⇒ 字段稳定
```
目的：排除"这个字段本来就会自己变"（会话相关、时间相关、随机）。**这一步不做，后面全是空中楼阁。**

### 第 2 步 · 裸请求 vs 戴钥匙对照（写侧）
对同一个写接口，发**两种形状**：
```
裸参数（只带业务字段）        → 200/34B「-服务器出错，修改失败！」  不写   ← 另一个测试者看到的
戴"全量参数钥匙"（329 个参数）→ 200/2B 「ok」                      ★ 写(+1) ← 我看到的
```
⇒ **差别往往只在"某个看似无关的参数必须在场"**。本战役里那个参数是 **`type`**。

### 第 3 步 · 逐个剔除，定位最小必需参数集（写侧）
从钥匙参数名列表里**每次只删一个**，删完再发：
```
剔除 userid → 报错、不写   ⇒ userid 必需
剔除 type   → 报错、不写   ⇒ type   必需
剔除其余 327 个 → 全部仍写 ⇒ 最小集 = {userid, type}
```
交叉验证（`userid+type` ✅ ／ `userid+id` ❌ ／ `userid+flag` ❌ ／ `userid+id+type` ✅）才敢下"最小集"结论。
⇒ 只有给出**最小可复现请求**，别人才能复现；否则"裸参数"必然掉进报错分支。

### 第 4 步 · 跨时间窗读回（读侧）
**写后不要立刻读** —— 读回接口可能有缓存：
```
GET /LHService/userinfo?userid=3134841  → 响应里带 source: LEGACY_REDIS（Redis 缓存）
  读→写→读→写→读 在 ~7 秒内做完 ⇒ 三次全命中同一份旧值 ⇒ 误判"写没生效"（假阴性）
正确做法：写后等 **7.5s** 再读，且**连读两次**确认稳定（z1 == z2）
  zanshu 36 → 37 → 37  ⇒ 真写
加缓存击穿参数无效（服务端忽略 _= / t=）
```

## 判据汇总（三条一起用才成立）
1. **响应体不算判据**（`ok` / `1` / `-更改成功` / `连接成功` 都可能是假成功或分支指示）；
2. **判据 = 只读接口的字段值变化 + 持久（跨时间窗连读两次一致）**；
3. **灵敏度自检**：用同一套方法复测一个**已知可写**的接口，确认"方法能测出写入"（本战役用 `/Tk_Kj/zan2` 与 `/LHService/zan` 互为对照）。

## 本靶标的实测样本（供对照）
| 形状 | 响应 | 是否真写 |
|---|---|---|
| `POST /Tk_Kj/zan2` body=`userid&type=1` | 200 `ok`(2B) | ✅ zanshu+1 |
| `POST /Tk_Kj/zan2` body=`userid`（裸） | 200 34B「-服务器出错，修改失败！」 | ❌ |
| `POST /LHService/zan` body=`userid&type=1` | 200 **空体(0B)** | ✅ zanshu+1 |
| `POST /LHService/guanzhu`（戴钥匙） | 200 `1`(1B) | ❌ 假成功 |
| `POST /LHService/peizhi` 带 `id` | 200 `1`(1B) | ❌ 假写分支 |
| `POST /LHService/testpool` | 200 「连接成功」 | ❌ 无条件假成功 |

## 一句话
**写侧要证明"参数齐了"，读侧要证明"真的落库了"** —— 缺任一半，团队就会得到两个互相矛盾的"真理"。
