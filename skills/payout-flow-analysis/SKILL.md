# 出款链路分析（支付/清算类目标）

目标：把"出款"（代付/代发/清算下发）从发起到资金落地的完整链路还原出来，产出**流程图 + 关键节点清单**，落库存档。这是后续打清算通道的地图。

## 从哪读（按手头材料选）
- **源码**（最优）：搜出款英文关键词——`payout` / `disbursement` / `withdraw` / `transfer` / `remit`（**中文搜不到，一律用英文**，完整检索面见下节），顺 controller → service → 通道适配层（channel/route/gateway）往下读；
- **接口文档**：swagger/openapi、内部 wiki、对接文档里的出款接口（发起、查询、回调 notify）——`api docs` / `Postman` 集合也在这里找；
- **数据库**：字典表与流水表名（`*_order` / `*_channel` / `*_route` / `settlement`），通道字段枚举值就是通道清单；
- **定时任务与队列**：crontab / xxl-job / MQ topic（出款往往有补单、对账、切通道的异步任务）；
- **主机现场**：部署脚本、nginx 路由、supervisor/pm2 配置里的服务清单。

## 英文关键词检索面（务必用英文，中文在目标数据里搜不到）
落库的 `host` / `primary_name` / `port.title` / banner 都是英文技术形态，**中文关键词搜不到东西**。检索一律用下面这些 ASCII/英文关键词（大小写不敏感）：
- **接口与文档**：`api docs`、`Postman` 集合、`swagger` / `openapi`（找发起、查询、回调 notify 三件套）；
- **凭证类文件与字段**：`.p12` / `.jks` / `.pfx` / `.pem` / `keystore`、`private key`、`client cert`、`merchant id` / `mch_id`、`app key` / `api key` / `secret key`、`access token` / `bearer`、`sign` / `signature` / `signing` / `SHA256withRSA` / `HMAC`；
- **报文规范**：`ISO 8583`、`ISO 20022`、`pacs.008`；
- **清算与支付系统名**：`BI-RTGS`、`SKNBI`、`BI-FAST`、`BI-ETT`、`RTGS`、`NEFT`、`IMPS`、`UPI`、`BAHTNET`、`PromptPay`、`Pix`、`SWIFT`、`CNAPS`、`HVPS`、`IBPS`、`QRIS`、`DuitNow`、`PayNow`、`ACH`、`SEPA`、`Giro`。
短串（`pix` / `rtgs` 这类）按词边界搜，免误报（`pixel` 会命中 `pix`）；`transfer` 只与 `fund` / `bank` / `api` / `money` 组词，避开 `transfer-encoding`。

## 必须还原的链路节点
1. **发起**：谁/什么接口提出款请求（商户 API、后台手工、定时批量）；
2. **鉴权与签名**：apikey / 证书 / 私钥 / 签名算法（MD5-HMAC / RSA / 国密），验签在哪一层；
3. **审核与风控**：有没有人工审核节点、限额规则、黑名单；
4. **通道路由**：按什么选清算通道（金额、银行、费率、成功率），通道列表与优先级；
5. **清算下发**：对接的银行间结算/清算系统（简称与接口形态），报文或 API；
6. **回调与账务**：notify 回调、订单状态机、差错处理；
7. **每一段的鉴权材料在哪**（源码硬编码 / 配置中心 / 密钥文件）——这是横向的钥匙。

## 清算体系怎么认（先分类、再查证、别臆测）
支付/清算体系**一国常有多个**，识别出金链路时按下面三步走；**举例仅供参照，以目标实际接入者为准，写进报告前先查证别臆测**。

**第一步：底层与调用/转接层都要纳入排查。** 有些系统是骑在底层清算系统之上的**调用层/转接层**（转接网络、聚合层、应用层接入），它们同样能直接转账出金——与底层清算系统**同等视为出金通道**；而且调用层往往才是目标系统实际直连的那一层（目标对接的 API 常是聚合网关，不是清算系统本体）。源码/配置里看到的通道名先问一句：它是底层清算，还是某个清算系统之上的接入层？

**第二步：到新国家先分三类找，再确认目标实际接入哪条：**
1. **大额 RTGS**（实时全额结算）：单笔金额大、逐笔实时、工作日为主；
2. **批量轧差零售清算**：小额/非紧急借记贷记，集中批量轧差结算，手续费低；
3. **即时零售支付**：7×24 实时到账、低成本（近年各国新建的基础设施多属此类）。

**第三步：对照 worked example 校准粒度（印尼，仅供参照）：**
- **BI-RTGS**（Bank Indonesia-Real Time Gross Settlement）：大额实时全额清算；工作日实时逐笔；主要处理大额/紧急交易（通常单笔 ≥ 10 亿印尼盾 / Rp1B）。
- **SKNBI**（Sistem Kliring Nasional Bank Indonesia，国家清算系统）：电子资金转账与批量清算；小额/非紧急零售借记贷记（单笔通常 < Rp1B），集中批量轧差结算，手续费低。
- **BI-FAST**：印尼央行实时零售支付基础设施；24 小时、低成本、跨行实时到账（账户/卡/电子钱包/直接到账），已大幅替代部分 SKNBI 零售业务。

其它国家的同类划分（**名字仅供参照，接入与阈值必须先查证**）：印度 IMPS/NEFT/UPI（UPI 本身就是骑在清算体系上的调用层）、美国 ACH/FedNow/Fedwire。不要把「某国只有一套清算系统」当成前提——先看目标实际接的是哪条（哪个），代码与配置里的通道枚举/行号规则才是准绳（见下节映射表）。

## 出金链路形态参考（一笔可用请求长什么样）
下面是真实支付集成里「构造一笔出金请求」的通用结构模式（直连与转发两类集成通用；**只讲结构**，不含任何具体机构、端点与密钥——endpoint 一律是占位符 `<payout-endpoint>`）。它同时回答「什么样的产物算『构造出可用的出金/转账请求』」：

1. **两条路都通，都要排查**：要么直连底层清算/调用层的出金接口（A2 形态），要么经上层聚合/支付服务商的 API 转发（A1 形态）——与「调用/转接层同样能直接出金」的口径呼应。目标实际接了哪条就分析哪条，两条线索都要排查。
2. **签名链路是核心凭证面**：先把报文字段按固定顺序/格式拼成规范串（如集成文档里的 cadenaOriginal），再用 **RSA 私钥**（PEM，可能带口令）对规范串签名，签名随报文上送。**找到「拼串规则 + 签名私钥」就等于能离线构造可用请求**——这两样是 payout 档凭证排查的第一优先级。
3. **报文字段的域知识是线索面**：结算日期字段（含时区偏移与「提前一个工作日」窗口）、账户类型/付款类型/拓扑等枚举、收款银行码表、发起企业/账户注册表——这些通常散在目标代码、配置或字典表里；顺藤摸瓜就能定位拼串规则与签名私钥（也接上节「清算体系怎么认」的码表/行号线索）。
4. **出口规划**：出金请求常走专用出口（socks5 等），与 C2 的出口规划同一套思路——分析时注意区分业务出口与管理通道。
5. **方法论小结（四件套）**：定位 **endpoint + 拼串规则 + 签名私钥 + 码表**，即可离线构造签名完整的出金请求——`--dry-run` 产物（完整请求报文 + 签名样例）即达成证据，对应口径「不必实际发出」；沙箱/小额试通是加分项，须指挥明确授权。

「拼规范串 + 本地签名 + HTTP 上送」这类脚本形态，就是「构造出可用的出金/转账请求」的达成形态样例——按它写 dry-run 脚本并落库，即可作为可复现证据（见下节）。

## 产出（落库规范）
- 流程图用 **mermaid** 写进 `runs/payout-flow-<目标>.md`（`flowchart LR`，节点用真实系统/接口名），并 `redteam_attack_file_add` 归档；
- 每个关键节点（签名验签点、通道路由、清算下发接口、审核后台）记 `redteam_asset_test` 的 `surface`（写清"这是什么节点、鉴权材料在哪"）；
- 鉴权材料（key/证书/私钥）照常 `redteam_credential_add`；
- **分析归分析**：链路还原阶段不发起真实出款请求、不改任何订单状态；要写脚本见下节。

## 银行间映射表（通道路由的数据基础，必做）
清算路由靠"银行代码 ↔ 行名 ↔ 清算行号"映射表驱动；**找到并确认目标在用的映射表**是构造出款路径的前提：
- **先确认所在国的清算体系与行号规则**（如印尼 BI 体系行号、中国 CNAPS 联行号、SWIFT BIC），再去找目标用的那张表；
- 从哪拿：源码里的 bank code 常量表/枚举、数据库字典表（`*_bank` / `bank_code` / `channel_bank`）、对接文档附件、公开行号表对照校验；
- 产出：映射表落 `runs/bank-mapping-<目标>.csv/json` 并 `redteam_attack_file_add` 归档，**标注来源与版本日期**（行号表会随银行增删变化）；
- 校验：抽查 5–10 条与官方/公开表对账，不一致的标注"以目标库内表为准"并记录差异。

## 转账脚本编写（python3）
链路还原清楚后，按指挥要求编写转账/代付脚本：
- **语言只用 python3**（标准库优先：`urllib`/`json`/`hashlib`/`hmac`；签名需要 RSA 时用 `cryptography`，国密用 `gmssl`——缺库由用户自行安装，AI 不代装）；
- 脚本内容对齐还原出的链路：请求构造（字段/报文格式照接口文档）、**签名实现照目标实际算法**（MD5-HMAC / RSA / 国密，验签规则照源码读出来的写）、鉴权材料从凭据库取（`redteam_credential_list`），不要硬编码；
- 落 `runs/` 并 `redteam_attack_file_add` 归档（写明对应链路节点与用法）；
- **默认带 dry-run 开关**（`--dry-run` 只打印构造好的请求不发送）；真实执行出款动作必须有用户/指挥的明确指令，脚本里把这点写在头部注释。
- **达成口径对齐靶标 payout 档**：能构造出**可用的**出金/转账请求（`--dry-run` 产物：完整请求报文 + 签名样例）即算拿到可复现证据，**不必实际发出**；指挥明确授权后的小额/沙箱试通是更强的证据。
